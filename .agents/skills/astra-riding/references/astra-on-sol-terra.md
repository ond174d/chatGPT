# Sol / Terra で Astra 並みに動かす

GPT-6 Astra を使わずに、Codex 上の GPT-5.6 Sol / Terra から Astra の振る舞いを引き出すための構成。
Astra と Sol の差は「判断のルール」と「素の能力」の 2 種類に分かれる。前者は指示と設定でほぼ埋まる。
後者は推論強度・検証工程・サブエージェントで補うが、完全には埋まらない。その境界を先に押さえる。

## 1. Astra と Sol / Terra の差分

Codex が各モデルに与えている組み込み指示を比較すると、Astra だけが持つ規則は次の通り。これが「指示で移植できる差」。

| 領域 | Sol の組み込み指示 | Astra の組み込み指示 |
| --- | --- | --- |
| 許可 | 新しい権限や外部調整が要るなら**ターンを止めて指示を求める** | 許可はセッションをまたいで持ち越す。承認が要るなら**作業を全部済ませてから最後に**聞く |
| 完遂 | 依頼種別に応じて対応(回答 / 診断 / 変更 / 監視) | 「できますか」は実行指示。計画提示や部分解で止まらない。スコープを削らない |
| 質問 | 前提を置いて進み、逸れるなら明示 | 結果を変える質問だけ早めに選択式で聞き、**待つ間も依存しない作業を続ける**。時間経過は承認ではない |
| 途中のメッセージ | 置き換えか追加かを判断し、置き換えなら前の作業を捨てる | 既定で**舵取り**として扱い、元の目的を保つ |
| 圧縮後 | 最後の依頼が現在の依頼 | 最新メッセージは舵取り。**元の目的・制約・完了済み・未完了を保持** |
| 検証 | リスクに比例して検証 | 比例に加えて「通ったら広げない」「実装を写すテストは書かない」「仮想リスクで警告を足さない」を明文化 |
| 文体 | 過度な装飾を避ける | AI 定型語・対比フレーミング・見出し・締め要約の禁止、PR 説明の書き方まで規定 |
| スキル | 一致したら必ず使う | 役立つときに判断で使う。スキルが原因で止まるなら該当行を引用 |

指示で埋まらない差(素の能力):

- 正直さ。System Card では、能力やツールについて誤った表現をする率が Sol は Astra の数倍。**「見た証拠のない主張をしない」規則と、独立した検証サブエージェント**で補う。
- トークン効率。同じ作業で Sol は Astra の約 3 倍のトークンを使う。並列化・再読の抑制・検証を広げない規則で削るが、差は残る。
- 推論の深さ。effort を一段上げ、難所だけ Sol の ultra(協調サブエージェント)を使う。
- 非同期の質問。Astra はハーネス側の非同期質問ツールで「聞きながら進む」。Sol でも同じツールがセッションにあれば使えるので、**あれば使う、なければ最終回答に質問と置いた前提を併記する**と指示する。
- context notes。Astra 向けの検索可能なノート機能は Sol では使えない前提で、**手動のノートファイル**(`.astra-notes.md`)を圧縮後に再読する運用で代替する。

## 2. 4 層の構成

| 層 | 何をするか | ファイル |
| --- | --- | --- |
| 1. 指示 | Astra だけが持つ規則を Sol の組み込み指示の上に重ねる | `assets/overlay.md`(オーバーレイ)、`assets/codex/astra-instructions.md`(全置換版) |
| 2. 設定 | モデル・effort・developer_instructions をプロファイルにまとめる | `assets/codex/config.toml` |
| 3. hooks | セッション開始時と圧縮後に規則カードとノートを再注入する | `assets/codex/hooks.json`、`assets/hooks/rulecard_hook.py` |
| 4. 検証 | 最終回答前に読み取り専用の検証サブエージェントで主張と差分を照合する | `assets/codex/agents/astra-verifier.toml` |

指示の入れ方は 3 通りあり、優先順位は `model_instructions_file` > AGENTS.md > ユーザーメッセージ。

- **オーバーレイ(推奨)**: `developer_instructions` と AGENTS.md の両方に同じ文面を入れる。組み込み指示はそのまま残るので、Codex の更新で追加される指示を失わない。Codex App では `developer_instructions` が付かない報告があるため、AGENTS.md 側が保険になる。
- **全置換**: `model_instructions_file` で組み込み指示を `astra-instructions.md` に差し替える。オーバーレイで足りないときだけ。Sol の組み込み指示にある編集・破壊的操作の規則は同ファイルに取り込んである。
- **hooks**: `SessionStart` で規則カード、`PostCompact` で圧縮後の継続規則とノートを注入する。イベント名と対応状況は Codex のバージョンで変わるので、動かない場合は `codex --help` か公式の hooks ドキュメントで名前を確認する。

## 3. 導入手順

```bash
# このリポジトリ(または任意のプロジェクト)の .codex/ と AGENTS.md に導入
python3 .agents/skills/astra-riding/scripts/install.py --project --target codex

# 全プロジェクト共通にする場合
python3 .agents/skills/astra-riding/scripts/install.py --global --target codex

# 起動
codex --profile astra-sol        # Sol
codex --profile astra-terra      # Terra
codex --profile astra-sol-full   # 組み込み指示を全置換する版
```

既存の `config.toml` はバックアップを取り、`# >>> astra-riding` マーカーで囲んだブロックだけを追記・置換する。再実行すればブロックが更新される。

導入後、`scripts/audit_instructions.py` を実行して、既存の AGENTS.md や SKILL.md にオーバーレイと矛盾する「常に確認」「決して〜しない」型の記述が残っていないか確認する。Sol は矛盾した指示があると回り道をしやすい。

## 4. モデル別の推奨設定

| モデル | 既定 effort | 上げる条件 | 備考 |
| --- | --- | --- | --- |
| gpt-5.6-sol | high | 設計判断・難しいデバッグは xhigh。xhigh で失敗した作業だけ max / ultra | ultra は内部でサブエージェントを起動するため 1 ターンのトークンが数倍になる。予算上限とセットで使う |
| gpt-5.6-terra | xhigh | 定型作業は high に下げてよい。設計が絡む作業は xhigh のまま | Sol より推論の余裕が少ないので、規則を守る余力を effort で確保する |

effort は品質・遅延・コストのダイヤルであり、上げれば必ず良くなるわけではない。「実タスクで失敗を確認した作業だけ上げる」を守る。

## 5. Sol / Terra の既知の癖と対策

| 癖 | 対策(どの層で) |
| --- | --- |
| 指示を読み飛ばす、途中で忘れる | hooks の `SessionStart` で規則カードを再注入。AGENTS.md と developer_instructions の二重化(層 1・3) |
| 明確な正攻法があるのに回り道する | 矛盾する古い指示を監査で削る。プロンプトで「正攻法を先に、代替は失敗してから」と明示(層 1) |
| 途中のメッセージで元の目的を落とす | オーバーレイの舵取り規則。長いタスクではノートファイルに目的と制約を書く(層 1・3) |
| 圧縮後にやり直す、完了済みを再実行する | `PostCompact` で継続規則とノートを注入(層 3) |
| 「変更した」「テストが通った」と言うが差分や出力がない | 「見た証拠のない主張をしない」規則。最終回答前に astra-verifier で差分と主張を照合(層 1・4) |
| 些末な点で止まって質問する、逆に重要な判断を黙って推測する | 3 種類の仕分け表をオーバーレイに明記。質問は選択式で束ねる(層 1) |
| トークンを多く使う | 並列化、再読の抑制、検証を広げない規則。ultra を常用しない(層 1・2) |

## 6. 埋まらない差と付き合い方

この構成で Sol / Terra は「判断のルール」については Astra とほぼ同じ形で動く。残る差は推論の深さと正直さの素の値で、次の運用で吸収する。

- 難所は Sol の xhigh、それでも駄目なら ultra を**その作業だけ**に使う。
- ロジック・データ・インフラに触れる変更は astra-verifier を必ず通す。検証の指示は親エージェント任せにせず、プロンプトに「最後に $astra-verifier に確認させて」と書く方が確実(Codex はカスタムサブエージェントを自動では起動しない)。
- 最終回答に「検証できなかったこと」の段落を求める。Sol が黙って通しやすい箇所を、報告の型で強制する。
- それでも Astra との差が業務上問題になる作業(長時間の自律作業、曖昧な仕様からの設計)は、その作業だけ Astra に切り替える判断を残しておく。
